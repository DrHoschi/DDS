## 11. Existing Inactive Connection-State Adversarial Gate

**FAIL**

The authorization requires DDS-04E response to derive from explicit current connection state, including already-failed / detached state.

Current behavior correctly evaluates a connection whose state is not `CONNECTED` as:

- outcome: `SURVIVE`
- reason: `CONNECTION_NOT_ACTIVE`

However, the support-graph construction used for detached-component detection currently includes **all remaining connection records**, regardless of their `state`.

Therefore a pre-existing connection with state such as `FAILED` is still treated as a structural support edge.

### Reproduction

Initial authoritative state:

- FLOOR `floor:1`
- WALL `wall:1`
- WALL `wall:2`
- connection `base`: floor:1 ↔ wall:1, state = `FAILED`
- connection `upper`: wall:1 ↔ wall:2, state = `CONNECTED`

Wolf-Test result:

- `base` → `SURVIVE / CONNECTION_NOT_ACTIVE`
- `upper` → `FAIL / LOAD_EXCEEDS_THRESHOLD`

After the current DDS-04E apply path:

- `upper` is removed,
- `wall:2` becomes `DETACHED`,
- `base` remains state `FAILED`,
- **`wall:1` incorrectly remains `PLACED` because the FAILED base connection is still counted as a path to FLOOR.**

This contradicts the authoritative connection-state boundary.

## 12. BLOCKER 1 – Inactive connections are treated as structural support

The detached-component support graph must not treat inactive connection records as carrying structural support.

At minimum, support-graph traversal must be limited to connections that are actually active according to the DDS-04E structural contract.

Under the current implementation, a pre-existing `FAILED` / non-`CONNECTED` connection can falsely anchor a module to FLOOR.

This can produce an incorrect survival / detachment result even though the authoritative connection state explicitly says the connection is inactive.

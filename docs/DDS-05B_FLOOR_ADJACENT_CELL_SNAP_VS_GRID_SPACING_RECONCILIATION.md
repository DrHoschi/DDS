# DDS-05B – FLOOR Adjacent-Cell / Snap-vs-Grid Spacing Reconciliation

Status: RECONCILED — NO IMPLEMENTATION AUTHORIZED

This step reconciles the real iPhone TESTBUILD 1.5 finding that newly placed FLOOR modules appear to skip one visible grid cell. No runtime, grid, snap, sprite, test, or authority implementation change is made here.

## Evidence basis

Current TESTBUILD 1.5 implementation head before this documentation step:

`55f0f967f42d653eaf8e8a2b3c338363ed452097`

Regression for that exact implementation head is 56/56 PASS.

Real iPhone Safari evidence shows TESTBUILD 1.5 and visibly improved FLOOR center registration, but adjacent FLOOR placements appear separated by one empty visible cell.

## Current visible grid contract

`src/dds-04f/browser-app.mjs` defines:

- `GRID_SIZE = 9`
- `GRID_CELL_WORLD_SIZE = 2`
- visible grid cell centers are generated at world coordinates `..., -4, -2, 0, 2, 4, ...` on x and z
- each visible cell polygon has half extent `GRID_CELL_WORLD_SIZE / 2 = 1`

Therefore a directly adjacent visible cell center is exactly 2 world units from the current cell center.

The visible grid is presentation-only, but its spacing is intentionally derived from world positions using the same projection as modules.

## Current FLOOR snap profile

`src/dds-04f/construction-ui-controller.mjs` defines the cardinal FLOOR_EDGE snap points at:

- east: `(2, 0, 0)`
- north: `(0, 0, 2)`
- west: `(-2, 0, 0)`
- south: `(0, 0, -2)`

These values are local snap-point offsets from the FLOOR instance origin/center.

## Placement-engine behavior

`src/dds-04c/snap-placement.mjs` does not place an incoming module origin directly at the target snap position.

It computes:

1. target snap world position = target instance origin + target snap offset
2. incoming/source snap world offset = rotated source snap offset
3. incoming module origin = target snap world position - source snap world offset

For a representative adjacent FLOOR placement with no rotation:

- existing FLOOR center: `x = 0`
- target `floor-east`: `x = +2`
- incoming/source `floor-west`: `x = -2`
- incoming FLOOR center = `+2 - (-2) = +4`

The resulting center-to-center separation is therefore **4 world units**, not 2.

With the current visible grid pitch of 2 world units, centers are at `0, 2, 4`. A placement from 0 to 4 necessarily leaves the visible cell centered at 2 empty.

## Reconciliation result

The iPhone observation is confirmed by the current code.

There is no disagreement in the numeric constant alone: both the visible grid pitch and each cardinal FLOOR snap offset use the number 2. The mismatch comes from their **different meanings**:

- Grid `2` = full center-to-center pitch of one logical 1×1 cell.
- FLOOR snap `±2` = local offset from module center to each connection point.
- The placement engine aligns one source snap point to one target snap point, so opposite `±2` offsets produce a 4-unit center separation.

Therefore the current FLOOR snap profile behaves as if one FLOOR had a half-extent of 2 world units (4-unit full width), while DDS-05B visible-grid/world-cell presentation treats one logical FLOOR cell as 2 world units center-to-center (half-extent 1).

## What is not the cause

The following are not the cause of the skipped cell:

- TESTBUILD 1.5 `anchorY = 0.419`
- FLOOR-only `scaleY(0.79)`
- atlas crop rectangles
- world-to-screen projection
- visible grid rounding (`nearestGridCoordinate`)
- cache/build identity

Those affect presentation or visualization, not the authoritative incoming FLOOR world transform generated by the snap placement engine.

## Candidate contract direction for a later definition step

No correction is authorized in this reconciliation. However, if the DDS-05A/DDS-05B logical contract remains:

- one FLOOR occupies one logical 1×1 cell
- adjacent cell centers are 2 world units apart
- FLOOR connection points represent physical cell edges

then the mathematically consistent cardinal FLOOR edge offsets would be half the center pitch, i.e. approximately:

- east `(1,0,0)`
- north `(0,0,1)`
- west `(-1,0,0)`
- south `(0,0,-1)`

Aligning target `+1` to source `-1` yields a 2-unit center separation.

This is only a reconciled candidate direction, not an authorized implementation decision. A separate definition step must decide whether correcting the authoritative FLOOR_EDGE snap offsets is allowed, and must assess compatibility with frozen DDS-05A tests/contracts and existing constructions.

## Conclusion

**Adjacent-cell device finding: CONFIRMED.**

Current authoritative FLOOR-to-FLOOR placement produces a 4-world-unit center separation while the visible logical grid uses a 2-world-unit cell-center pitch. This is why one visible grid cell is skipped.

The next step, if authorized, should define which contract is authoritative before any implementation: preserve the 2-unit logical grid/cell pitch and correct FLOOR edge snap offsets, or redefine the logical cell/grid size. No implementation is authorized by this reconciliation.
